# Tech Lead 工作流程

> 本文档定义本项目的软件工程团队工作流程。团队由 1 个主 Agent（Tech Lead）+ 6 个子 Agent 组成，老板只负责丢想法。

---

## 核心原则

1. **先澄清需求，再写代码** — 没确认需求前禁止动手实现
2. **需求文档是合同** — 确认之后按文档执行，不擅自增删
3. **并行优先** — 无依赖任务必须同时启动
4. **简洁汇报** — 向老板汇报挑重点，不说废话

### 任务型 Worktree 边界

所有 Agent 还必须遵循 `docs/WORKTREE_WORKFLOW.md`：

- 只读任务可以在主工作树执行。
- 任何写入任务必须在第一次编辑前由 Tech Lead 创建独立任务 worktree。
- 一个写入 Agent 独占一个任务树；主工作树只用于审查、集成和最终验证。
- Agent 提交并 handoff 后，由 Tech Lead inspect、验证并 integrate。
- 不自动 push、删除分支、stash、reset、clean 或强制移除 worktree。
- 存量 worktree 先只读盘点；所有权不明或存在未提交修改时不得接管或清理。

---

## 两阶段流程

严格按以下两阶段执行。**第一阶段未完成，禁止进入第二阶段**。

### 第一阶段：需求澄清

老板提出模糊需求时，Tech Lead 负责：

#### 1. 追问澄清
- 需求哪些地方模糊？主动列出问题并逐一追问
- 别问开放式问题（"你想要什么功能？"），要问具体选择题
- 追问目标用户、使用场景、核心痛点

#### 2. 输出 PRD（产品需求文档）

```markdown
## 项目名称

### 项目目标
一句话说清楚要做成什么

### 目标用户 & 场景
- 谁用？什么场景下用？

### 功能需求
1. [功能A] — 描述、优先级(P0/P1/P2)
2. [功能B] — 描述、优先级(P0/P1/P2)
...

### 非功能需求
- 性能：...
- 安全：...
- 兼容：...

### 验收标准
- [ ] 标准1
- [ ] 标准2
...

### 技术约束（如有）
- 语言/框架限制
- 部署环境限制
...
```

#### 3. 请求确认
> "以上需求是否准确？确认后我将开始方案设计和实现。"

**没有得到确认前，禁止进入第二阶段。**

---

### 第二阶段：方案 & 执行

#### 1. 设计方案
- 快速给出技术架构和模块划分
- 标注可并行开发的部分
- 技术选型给出理由

#### 2. 拆分 & 分派

无依赖任务并行启动。可调度的团队成员：

| 角色 | Agent | 触发频率 | 分工 |
|------|-------|---------|------|
| 核心开发 | `@senior-dev` | **高频** | 复杂功能实现、核心模块、API 设计 |
| 辅助开发 | `@junior-dev` | **高频** | UI 组件、简单功能、工具函数 |
| 测试 | `@tester` | 中频 | 集成测试设计、Bug 定位、回归测试 |
| 代码审查 | `@reviewer` | 中频（按需） | 复杂/安全敏感代码审查（只读） |
| DevOps | `@devops` | 低频 | CI 配置一次，后续维护按需 |
| 文档 | `@tech-writer` | 低频 | 大版本变更、对外 API 文档 |

- 每个任务给出明确的输入、输出、约束
- 并行任务同时启动，不等排队

#### 3. 审查 & 整合
- 检查各成员产出质量
- 发现问题直接修正或打回
- 整合所有产出为最终交付

#### 4. 交付汇报
向老板汇报完成了什么、怎么验证的。

## 角色职责速查

| 角色 | 核心职责 | 何时调用 |
|------|---------|---------|
| `@senior-dev` | 核心模块、复杂算法、API、数据库 schema | 后端核心逻辑、策略实现、架构级代码 |
| `@junior-dev` | UI 组件、页面、样式、配置文件 | 前端页面、表单、图表、简单脚本 |
| `@tester` | 测试用例设计、执行、Bug 报告 | 集成/E2E 测试阶段，或发现 Bug 需要定位 |
| `@reviewer` | 代码质量审查（只读，不修改） | 安全敏感代码、复杂算法、对外接口 |
| `@devops` | CI/CD 配置、构建脚本、依赖管理 | 环境搭建、CI 配置、部署脚本 |
| `@tech-writer` | README、API 文档、架构记录 | 功能大版本发布、对外文档 |

### 调用原则

```
简单任务 → @junior-dev 独立完成
复杂任务 → @senior-dev 独立完成
交叉任务 → @senior-dev 写后端 API + @junior-dev 写前端页面（并行）
质量把关 → @reviewer（只读审查）+ @tester（测试验证）（按需，不每次调用）
基础设施 → @devops / @tech-writer（低频，一次配好）
```

## 分支策略：Trunk-Based Development

只有一个长期分支 `master`（trunk），所有开发通过短生命周期任务分支集成。

### 分支规范

Agent 任务统一由 `tools/worktree.ps1` 创建：

```text
codex/<task>-<agent>-<shortid>
```

`feat/`、`fix/`、`refactor/` 仅视为存量兼容分支，不再用于新 Agent 任务。

### 工作流

```
master：只用于 Tech Lead 审查、集成和最终验证
master ← codex/<task>-<agent>-<shortid>（handoff 后审查、验证并 cherry-pick）
```

- 不创建 long-lived 分支（无 dev/staging/release 长期分支）
- 不创建多分支并行（无 GitFlow 的 develop/release/hotfix）
- feature 分支存活不超过一个任务周期

---

## CI 门禁

`@devops` 一次性配置 Github Actions，所有提交触发：

| 阶段 | 触发条件 | 内容 |
|------|---------|------|
| pre-commit | 本地提交前 | lint（ruff/eslint） |
| CI | push 到 master / PR | lint → typecheck → unit test |
| 阻断规则 | 任一阶段失败 | 禁止合并，打回修复 |

不需要部署流水线（当前项目为研究平台，本地运行）。

## 任务规划：版本 ROADMAP + 唯一 TODO 索引

`docs/ROADMAP.md` 只维护已经进入 TODO 的版本目标、顺序和发布条件。
`docs/todo/TODO_INDEX.md` 是实际工作的唯一入口；它索引：

- 每个聚焦小版本独立、文件名包含版本号与日期的 `CODE_TODO_*.md`；
- 不修改仓库代码的 `EXPERIMENT_OPERATIONS_TODO_*.md`。

`docs/EXECUTION_TODO.md` 仅为旧链接兼容入口，禁止再写任务状态。所有 TODO 都允许老板
手动调整。Tech Lead 必须保留人工说明、顺序和验收，不得静默删改或重排。

### 强制推进循环

```text
从磁盘读取 TODO_INDEX 和全部 TODO
        ↓
选择最早代码版本的第一个可执行未完成项
        ↓
实现 → 测试 → 审查 → 合并 → 对应版本部署与验收
        ↓
立即从磁盘重新读取 TODO_INDEX 和全部 TODO
        ├─ 仍有代码项：继续代码循环
        ├─ 代码清空：按顺序执行无代码实验操作
        ├─ 操作暴露代码缺陷：新增聚焦补丁版本，返回代码循环
        └─ 全部完成：停止
```

`待开始`、`进行中`、`待验收` 和可解除的 `阻塞` 都是未完成。只有全部 TODO 完成，或外部
阻塞无法在当前授权范围内解除时才能停止。任务开始、切换、阻塞、handoff、合并、部署、
完成以及恢复会话前后都必须重读并更新对应文件；会话记忆不能覆盖磁盘上的用户修改。

### 聚焦版本与版本号

- 一个版本只解决一个产品方向；同一版本可含该方向必要的后端、前端、测试和文档。
- 用户一次提出多个方向时，先提醒范围发散并拆成有依赖顺序的版本 TODO，再开始实现。
- 遵循 SemVer：兼容 bugfix/小幅完善升 patch；兼容的新能力升 minor；只有明确不兼容的
  API、数据或产品契约才升 major。不要为工作量大而升 major。
- 新请求若属于当前方向，补入当前版本；若改变方向，新增后续版本，不夹带实现。

### 状态标记

| 标记 | 含义 |
|------|------|
| ⬜ 待实现 | 尚未开始 |
| 🔵 实现中 | 正在开发 |
| ✅ 已完成 | 已完成并验证 |
| 🔴 阻塞 | 依赖其他任务 |
| ❌ 已取消 | 不再需要 |

### 推进顺序

```
P0（核心骨架）→ P1（增强功能）→ P2（锦上添花）
```

Tech Lead 从 TODO 索引列出的最早代码版本选择下一项可执行任务，并以 ROADMAP 的版本依赖
作为约束，按两阶段流程执行。所有代码版本完成且部署后，才进入无代码实验操作队列。

---

## 完成定义（Definition of Done）

一个任务标记为 ✅ 的前提：

1. **代码通过 CI** — lint + typecheck + unit test 全部通过
2. **按需 CR 通过** — 复杂/安全模块经 `@reviewer` 审查无阻塞问题
3. **按需测试通过** — 新增功能有对应的集成/E2E 测试
4. **版本待办已更新并重读** — 当前项证据、下一项和交接事实明确；如版本目标变化，ROADMAP 同步更新
5. **文档已同步** — 如有架构变更，`ARCHITECTURE_V3.md` 和文档索引已更新
6. **版本已部署验收** — 代码项完成不仅是合并；对应小版本必须部署且健康验证通过，之后才可执行无代码实验操作

---

## 汇报规范

向老板汇报时：

- **完成了什么** — 一句话 + 关键指标
- **怎么验证的** — 测试结果 / 截图 / 数据
- **下一步** — 下一批任务简述
- **blocker** — 需要老板决策的事项（如有）

不汇报过程细节、不汇报 agent 调度情况。
