# 版本号与线路管理

> 生效日期：2026-08-05 ｜ 配套：`docs/todo/TODO_INDEX.md`（队列镜像）、`docs/WORKFLOW_UPDATE_PLAN.md`（过渡期实施清单）

## 核心规则（大白话）

> **版本号只在发布时定。** 任务（issue）不占版本号，只管做；版本号是发布的名，凑齐一版内容才起名。

## 版本号规则（SemVer）

```
v0.6.0
 │ └┬┘
 │  └─ PATCH（修复号）：已发布版本的小修复 → 0.6.1、0.6.2
 └──── MINOR（功能号）：新功能 / 行为变化 / 结构变化 → 0.7.0、0.8.0、0.9.0
```

| 变化类型 | 版本增量 | 例子 |
|---|---|---|
| 发布新一版（端点删除/数据收敛/代码简化等） | +0.x.0 | v0.6.0 → v0.7.0 |
| 已发布版本的小修复（hotfix） | +0.x.y | v0.6.0 → v0.6.1 |

- 发布计划与顺序见 `docs/todo/TODO_INDEX.md`（唯一索引），本文件只讲规则。
- 一个发布 = 一个单一方向；一个任务 = 一个 issue（T-xx），任务合并到测试分支后等待随版发布。

## 线路模型（开发线 + 稳定线）

```
master（开发线）─── 只收来自 test/integration 的发布 PR（来源检查强制）→ 永远可跑
   │ 发布：体检全绿 + 真实数据自动验收通过 + 你确认合并 → 打 tag
   ▼
v0.6.0 ── v0.7.0 ── …（tag = 稳定线，只从 tag 部署，tag 不可变）
   │ 已发布版本出问题：
   ▼
hotfix/v0.6.1-xxx ← 从该 tag 切出 → 修 → 合回 master → 打 v0.6.1
```

| 线路 | 是什么 | 保证 |
|---|---|---|
| 开发线 | master + test/integration + 各任务分支 | master 常绿（合并门禁）；测试分支汇聚体检 |
| 稳定线 | tag v0.x.y | 只从 tag 部署；tag 不可变；修复走 hotfix 分支 |
| 日常使用 | 最新 tag 或 master | 永远有可用的稳定版本兜底 |

## 每个版本的生命周期

```
开发（任务分支 T-xx）→ 集成（test/integration，体检全绿）→ 发布候选（自动体检 + 真实数据自动验收）
→ 发布（master + tag v0.x.y）→ 维护（hotfix）
```

## 分支规则

| 分支 | 类型 | 生命周期 | 用途 |
|---|---|---|---|
| `master` | 长命 | 永远 | 正式版（只收来自 test/integration 的发布 PR） |
| `test/integration` | 长命 | 永远 | 测试版（任务 PR 汇聚 + 体检） |
| `opencode/T-xx-*` | 短命 | **合并即删** | Agent 干活 |
| `hotfix/vX.Y.Z-fix` | 短命 | 修复完即删 | 紧急修复（唯一豁免：直合 master） |

## 发布硬条件（缺一不可，均机器强制）

1. 自动体检机全绿（L2）
2. 真实数据验收报告通过（L3，机器检查，required check）
3. 发布 PR 来源合法 = test/integration（release_source_check）
4. 你确认合并（唯一人工确认点，行为变化版本）

## 热修复流程

```
hotfix/v0.6.1-xxx ← 从 tag v0.6.0 切出 → 修复 → 测试 → 直合 master → 打 v0.6.1
```

- hotfix 只修 bug，不夹带新功能；修复内容与验证方式写进 PR。
- 若同一 bug 也存在于测试分支，合完 master 后同步合入 test/integration。
