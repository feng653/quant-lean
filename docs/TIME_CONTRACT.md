# 时间字段契约

量化平台研究链路的时间字段采用“数据库保留、UTC 传输、上海时区展示”的
统一契约。本次覆盖实验、参数方案、研究清单和策略关联实验接口；其他存量
模块的无时区响应由同一前端解析规则兼容，并应在后续 API 修改时迁移到该
UTC 出口契约。

## 契约

- 数据库存储：现有 SQLite `datetime('now')` 生成的
  `YYYY-MM-DD HH:mm:ss` 是无偏移标记的 UTC。继续保留这些值，不迁移、不加
  8 小时，避免改变历史时刻。
- 研究 API 传输：`created_at`、`updated_at`、`started_at`、
  `completed_at` 等时间戳统一输出 RFC 3339 UTC，例如
  `2026-07-30T00:00:00Z`。
- 前端展示：研究与任务页面通过共享时间工具解析，并明确用
  `Asia/Shanghai` 展示；上例显示为 `2026/7/30 08:00:00`。
- 日期区间：`train_start`、`train_end`、`test_start`、`test_end` 和行情
  `date` 是交易日，不是时间戳，继续使用 `YYYY-MM-DD`，不做时区换算。

## 兼容规则

API 出口把旧 SQLite 无时区值解释为 UTC；带 `Z` 或显式偏移的值按其真实
时刻换算为 UTC。前端共享工具也保留同样的旧值兼容分支，以便读取旧服务响应
或浏览器缓存，但新 API 响应不得再依赖该分支。

禁止在页面中直接调用 `new Date(apiValue)` 展示后端时间。应使用
`formatBackendDateTime`；需要计算持续时间时使用 `parseBackendTimestamp`。

## 验证

时间相关改动至少验证：

1. SQLite UTC 无时区值输出带 `Z`；
2. 显式 `+08:00` 输入保持同一瞬间，而不是重复加 8 小时；
3. 上海展示相对 UTC 正确增加 8 小时；
4. 空值或非法值不会在界面显示 `Invalid Date`；
5. 实验列表、实验详情、策略详情和参数方案使用同一格式。
