# 版本号与线路管理

## 版本号规则（只在发布时定，无需人懂 SemVer）

- **任务用 T-xx 编号**（发布 issue 时分配，持续递增），**版本号只在发布时定**。
- 每提一个新需求（issue），协调者回答一个问题：**"这个需求会改变接口/行为吗？"**

| 回答 | 版本增量 | 例子 |
|---|---|---|
| 否（纯重构、加测试、修 bug） | +0.0.1 | v0.6.0 → v0.6.1 |
| 是（改端点、删功能、改数据结构） | +0.1.0 | v0.6.x → v0.7.0 |

- 一个版本 = 一个发布名 = 一组已完成候选任务的集合。任务不占版本号。
- 任务状态与归属记录在 `docs/todo/TODO_INDEX.md`（GitHub issue 的只读镜像）。
- 发布序列只排"用户要求的"，补完当前发布再排下一版。

## 线路模型（trunk + tag + 按需 hotfix）

```
master（开发线）─── 只收"CI 绿 + 三层门禁通过"的发布 PR → 永远可跑
   │ 每版本发布后：打 tag
   ▼
v0.6.0 ──v0.6.1── v0.7.0 ── …（tag = 稳定线，只从 tag 部署）
   │ 已发布版本出问题：
   ▼
hotfix/v0.6.1-xxx ← 从该 tag 切出 → 修 → 合回 master → 打 v0.6.2
```

| 线路 | 是什么 | 保证 |
|---|---|---|
| 开发线 | master + 各 agent 分支 | master 常绿（发布门禁）；分支相互隔离 |
| 稳定线 | tag v0.x.y | 只从 tag 部署；tag 不可变；修复走 hotfix 分支 |
| 日常使用 | 最新 tag 或 master | 永远有可用的稳定版本兜底 |
