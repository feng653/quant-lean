## 1. 结论

路线图中的黄色与阻断项不是一种工作。当前 21 项 NEXT 可按关闭条件分成四类：

| 类别 | 含义 | 关闭规则 |
|---|---|---|
| C：代码/测试 | 仓库内可以继续实现并以隔离测试证明 | lint、单元/集成、故障注入和代码审查均通过；仍不能替代真实数据或服务验收 |
| R：本机运行 | 必须在正式 LaunchDaemon、真实数据库、浏览器或远端介质上形成证据 | 保存时间、commit、输入 hash、命令/浏览器结果、RPO/RTO 与失败证据；合成环境不算 |
| E：外部输入 | 依赖供应商账号、字段许可、权威材料、外部通知端或现实观察窗 | 取得书面许可和真实样例，或走完规定观察窗；仓库代码不能将其自动改成完成 |
| L：永久硬锁 | 在个人研究平台当前设计范围内应保持未关闭 | 真实送单、实盘 readiness 和绕过晋级/风控必须继续 fail-closed；只有独立新决策才能重开 |

截至本次审计，最值得立刻修复的可执行缺口是 NEXT-13：远端恢复命令在本地已有同名
归档时会跳过下载，因此可能把本地副本检查误报成“远端恢复”。本次已改为**每次强制读取
private Release**，在临时目录核对 GitHub asset size/digest、本机 SHA-256 和加密归档头，
通过后才原子发布；同名本地文件不能再绕过网络读取。回归测试覆盖了该反例。

这只关闭 NEXT-13 的代码假阳性，NEXT-13 仍为 `🟨`：必须从真实远端下载现有约 507 MB
密文、解密、完成四库 `integrity_check`，并在隔离目录重建服务、记录 RPO/RTO 后才能改为
`✅`。本次没有在开发 worktree 中启动服务或大文件下载，避免干扰正式进程。

## 5. NEXT-13 实机验收清单

合并、安装最新版后，选择 private Release 上已完成上传且本地有密钥的归档，以普通
`xuhe` 用户依次运行：

```sh
/usr/local/sbin/quant-platform-backup-repository.sh download-verify \
  <archive-basename.qpbak>
/usr/local/sbin/quant-platform-restore-drill.sh \
  <archive-basename.qpbak>
```

验收记录必须同时满足：

1. `backup-repository-audit.jsonl` 新增
   `operation=encrypted_release_download_verify,status=verified`，开始/完成时间发生在本次
   演练；不能复用旧记录；
2. 归档 size 与 GitHub asset digest、本机 SHA-256 一致；同名本地归档存在时远端下载
   仍真实发生；
3. `restore-drills/reports/*.restore-audit.json` 显示 AES-GCM、manifest、四个必需 SQLite
   库 `integrity_check` 全部通过；
4. 在不连接生产写入者的隔离目录/进程启动恢复代码，健康检查、登录、实验只读查询通过；
5. 保存远端下载耗时、解密/检查耗时、归档生成时刻与演练时刻，计算实测 RPO/RTO；
6. 临时明文恢复目录自动删除，密钥、`.env`、token 和数据库内容未进入日志或 GitHub；
7. 任一步失败均保持 NEXT-13/RT-P0-14 为黄色并生成失败记录，不覆盖生产数据库。
